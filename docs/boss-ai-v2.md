# 보스 AI v2 설계: Rapfi로 보정한 자체 엔진

2026-11-27 결정. 사이트에 들어가는 것은 자체 `ai.js`와 데이터뿐이다. Rapfi는 이 PC에서 채점·자기대국·보정에만 쓴다. Rapfi를 사이트에 넣는 일은 나중에 **히든 보스**(보스 위 단계)로 따로 한다(맨 아래 절).

## 목표와 기준

보스가 지는 원인은 두 가지다(`docs/boss-ai.md`).
- 평가 함수가 5칸 구간 안의 돌 개수만 센다. 열린 3, 닫힌 3, 띈 3을 구분하지 못한다.
- 후보 12수를 대략적인 `gain` 점수로 고른다. 그래서 조용한 준비 수(띈 3, 2-2)를 놓친다.

v2는 Rapfi를 정답지로 삼아 이 두 가지를 숫자로 재고 고친다. 기준 지표:

| 지표 | 뜻 | 목표(초안) |
|---|---|---|
| **M1 후보 적중률** | Rapfi 최선수가 보스 후보 목록 안에 드는 비율 | 98% 이상 |
| **M2 실착률** | 보스 수 직후 Rapfi 평가가 크게 떨어지는 수의 비율(기준값은 P3에서 정함) | v1의 절반 이하 |
| **M3 대국** | 새 보스 vs 옛 보스, 새 보스 vs Rapfi(고정 제한) 각 40판 | 옛 보스 상대로 우세, Rapfi 상대 승률 상승 |

사람 대국 기보(구글 시트, `docs/boss-book.md`)도 같은 채점에 넣는다.

## 규칙

한국식 규칙(흑만 3-3·장목 금지, 흑 4-4 허용, 백 장목 승리)을 유지한다. 렌주와 다른 점은 **흑 4-4 허용 하나**다(백 장목 승리는 렌주와 같음, `ai.js` `made5`).

Rapfi는 한국식을 모른다. 이 PC의 Rapfi 복사본에서 렌주 금수 판정의 4-4 금지만 푼다.
- 개인 PC에서만 쓰므로 GPL 배포 의무는 없다.
- 이 패치와 검증은 히든 보스에서 그대로 다시 쓴다.
- 평가표와 모델은 렌주 기준이라 흑 4-4 국면의 판단이 조금 어긋날 수 있다. 그래서 4-4가 걸린 국면은 데이터에 표시해 두고, 보정할 때 따로 본다.

## 단계

### P0. 엔진 준비 (PC 전용, 저장소 밖)
- 위치: `/Users/green/orca/engine/rapfi`(저장소 밖). 소스는 `github.com/dotb1ue/rapfi`(GPL-3.0). 고전 평가 모델 1개는 `rapfi-networks/classical`(CC0, 25~67KB).
- macOS 네이티브 빌드(CMake). WASM 빌드는 하지 않는다(히든 보스 때 한다).
- 한국식 패치:
  1. 금수 판정을 호출하는 곳을 소스에서 전부 찾는다.
  2. 4-4만 허용한다.
- 검증용 4-4 국면 세트를 만든다. 엔진이 흑일 때 4-4로 이기는지, 상대가 흑일 때 4-4를 막는지 확인한다. 3-3과 장목 금지가 그대로인지도 본다.
  - 세트와 실행 스크립트는 저장소에 둔다(엔진 코드는 없음, 엔진 경로는 환경변수).

### P1. 연결 도구 (저장소, `tools/engine/`)
- Gomocup(Piskvork) 프로토콜 클라이언트(Node). `START 15`, `INFO rule`, `INFO timeout_turn`/노드 제한, `BOARD`, `TURN`.
- 기능 두 가지:
  - 국면 → Rapfi 최선수 + 평가값
  - 자기대국 진행
- 엔진 실행 파일 경로는 환경변수 `RAPFI`. 저장소에는 우리 스크립트만 둔다.
- 평가값을 읽는 방법(상세 출력 옵션)은 P0 빌드 후 확인한다.

### P2. 데이터 모으기
- **자기대국**: 보스(`ai.js`) vs Rapfi(제한 몇 단계). 시작 4수는 `tests/duel.js`처럼 무작위로 둬서 다양하게 하고, 흑백을 바꿔 둔다.
- **채점**: 보스의 모든 수에 대해 국면, Rapfi 최선수, 평가값, 보스가 둔 수, 보스 후보 목록을 저장한다.
  - 같은 국면에서 둔 Rapfi 수도 함께 저장한다(평가 보정용 학습 데이터).
- **사람 기보**: 시트의 보스 대국도 같은 형식으로 채점한다.
- 출력: `positions.jsonl`(저장소 밖, 용량 큼). 저장소에는 요약과 재현 명령만 남긴다.

### P3. 진단 (v1 기준선)
- 지표:
  - M1(후보 크기 K별 적중률)
  - M2(평가 하락 기준값별 실착률)
  - 실착 국면에서 놓친 수의 모양별 분류. `tests/analyze-losses.js`의 모양 판정을 다시 쓴다.
- 결과를 `docs/boss-ai.md`에 기록한다. 여기서 B의 우선순위를 다시 정한다.

### P4. B 구현 (`ai.js`, 데이터로 보정)
1. **패턴표 평가**
   - 각 줄의 모양을 코드로 바꾸고, 표에서 점수를 읽는다. 돌을 놓을 때 바뀐 줄만 다시 계산한다(증분 갱신).
   - 표의 구조(어떤 모양을 구분하나)는 우리가 정한다.
   - **점수 값은 Rapfi 평가에 맞춰 오프라인으로 맞춘다**(로지스틱 회귀, Texel 방식).
   - 맞춘 점수표는 데이터라서 `ai.js` 안의 상수로 넣는다.
2. **후보 고르기**
   - 준비 수(띈 3, 2-2, 4-3 자리)를 점수와 상관없이 항상 넣는다.
   - 후보 점수 공식과 K는 M1 목표를 만족하는 가장 작은 값으로 정한다.
3. **위협 끝까지 읽기**: 탐색 끝 국면에 4나 열린 3 위협이 남아 있으면 조금 더 읽는다. VCT를 준비 수까지 넓힐지는 P3 결과를 보고 정한다.
- 측정 도구 `tests/duel-record.js`에 새 보스 vs 옛 보스, Rapfi 상대 모드를 더한다.
- 한 번 바꿀 때마다 M1·M2(빠름)를 먼저 보고, 큰 변경 때만 M3(느림)를 돌린다.

### P5. 배포
- **폰 시간 확인**: 배포 전에 사용자 폰에서 보스 한 수 시간을 잰다(측정용 숨은 기능 또는 테스트 페이지).
- **시간 기준**: 지금 기준(탐색 3.5초 + 필승 탐색)을 넘으면 깊이 대신 후보를 줄인다.
- ZESTMOK에 머지·배포한 다음, OhOhMok에 `ai.js`만 옮긴다(공용 학습 `ai-book.js`는 형식이 같으면 그대로 쓴다).
- 보스를 이겼던 두 사람에게 다시 도전을 부탁한다.

## 사이트에 들어가지 않는 것
Rapfi 실행 파일, 소스, 신경망 모델, 자기대국 원본 데이터. 사이트에 들어가는 것은 `ai.js`(우리 코드와 맞춘 점수표)와 공용 학습 데이터뿐이다.

## 히든 보스 (나중, 지금은 만들지 않음)
보스 위에 Rapfi(WASM, Web Worker)를 히든 보스로 둔다. v2를 하면서 다음을 미리 염두에 둔다.
- **다시 쓰는 것**: P0의 한국식 패치와 4-4 검증 세트, P1의 프로토콜·채점 도구(세기 단계 측정에 그대로 씀).
- **연결 지점**: 지금 UI는 `GomokuAI.bestMove`를 동기로 부른다. 히든 보스는 Worker라 비동기다. 그때 `doAiMove`를 비동기 호출로 바꾼다(지금은 바꾸지 않음).
- **진행 전 확인할 것**:
  1. 맥에서 emsdk로 단일 스레드 WASM 빌드가 되는지
  2. 금수 판정 호출부를 전부 찾았는지(P0에서 확보)
  3. 패치 후 4-4 국면에서 엔진이 흑일 때·상대가 흑일 때 모두 올바른지(P0에서 확보)
  4. 폰(구형 포함)에서 한 수 시간. 고전 모델 기준, 노드 제한별로 잰다
  5. Rapfi 세기 옵션(노드·깊이·시간)이 실제로 만드는 단계. 단계마다 v2 보스와 40판씩 둬서 승률을 본다
  6. GPL 처리 방식. 사이트 전체를 GPL로 공개할지 정한다. 그 전에 라이선스 파일 위치를 정리한다
  7. 상 엎기 판정에 쓸 평가값 기준선이 실제 "정말 졌다" 시점과 맞는지
- **불확실한 것**:
  - Worker 메시지 통신이 GPL상 결합이 아니라는 해석
  - 세기 조절이 충분히 세밀한지
  - 흑 4-4 평가 어긋남이 실전에서 얼마나 문제인지
  - 폰 성능(가장 먼저 잴 값)
